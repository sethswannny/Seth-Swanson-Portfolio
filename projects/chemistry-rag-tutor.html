Problem

Students ask the same course questions in different words.

A chemistry class has scattered information: the syllabus, exam calendar, lab handouts, safety rules, unit notes, and study guides. The goal is to make that material searchable through natural language while keeping answers grounded in the actual course documents.

Use Cases

It handles logistics and learning support.

The assistant can answer "When is the Unit 4 test?", "What should I bring to lab?", and "How do I do stoichiometry?" For tutoring questions, it explains the method step by step and points back to the relevant notes or study guide section.

App Structure

The important work is the retrieval system behind the chat.

I would not position this as a generic chatbot. The product is a course-specific retrieval system. The teacher controls the source files, the app breaks those files into searchable chunks, and every student answer is grounded in retrieved syllabus, calendar, lab, or study-guide content.

That matters for chemistry because students ask both administrative and instructional questions. "When is the Unit 4 test?" needs an exact calendar lookup. "How do I do stoichiometry?" needs a teaching-style explanation, but it should still pull from the class notes so the response matches the way the teacher introduced the method.

The working files in this project show the same shape in miniature: sample course documents, a local retrieval script, and a browser prototype. A production version would swap the keyword retriever for embeddings, a vector database, and an LLM answer step.

If 10.0 g of H2 reacts with O2, how many grams of H2O can form?
Worked example: grams H2 to grams H2O
  1. Balance: 2H2 + O2 -> 2H2O.
  2. Convert H2 to moles: 10.0 g / 2.016 g/mol = 4.96 mol H2.
  3. Use the mole ratio: 2 mol H2 makes 2 mol H2O, so 4.96 mol H2 makes 4.96 mol H2O.
  4. Convert to grams: 4.96 mol x 18.015 g/mol = 89.4 g H2O.

Assuming oxygen is available in excess, the theoretical yield is about 89.4 g of water.

Architecture

Course documents become searchable source chunks.

The system would ingest PDFs, Docs, and markdown notes; split them by headings, dates, and problem types; embed the chunks; and retrieve the most relevant passages before calling the model. The answer prompt would require citations, uncertainty language, and a fallback when the source material does not contain the answer.

Evaluation

The project can be tested like a real AI product.

I would build a small evaluation set of expected questions, including exam dates, late-work rules, safety requirements, and multi-step chemistry problems. Each response would be checked for retrieval relevance, citation quality, answer correctness, and whether it avoids inventing unsupported policies.

2. Retrieval

The demo ranks relevant chunks before answering.

The local Python version and browser version both load course chunks, score them against the question, and return only the most relevant sources. In production, this scoring step becomes embedding similarity. 

def retrieve(question, chunks, limit=3):
    query_terms = tokenize(question)
    scored = []
    for chunk in chunks:
        score = overlap(query_terms, chunk)
        if score:
            scored.append((score, chunk))
    return top_matches(scored, limit)

3. Grounded Answer

Answers cite the material they used.

A real LLM call would receive the retrieved chunks and a prompt that requires citations. If retrieval fails, the assistant should say it cannot find the answer instead of inventing a date, policy, or grade.
